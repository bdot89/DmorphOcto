# DMorph for OctoWoW

A WoW 1.12 addon: a morph window (models, races, items, wardrobe) plus DMorph-style chat commands for the OctoWoW client (modified 1.12.1, build 5875). See README.md for features and install.

The live copy is the game's `Interface\AddOns\DmorphOcto` folder, a git checkout of `main` (github.com/bdot89/DmorphOcto). Edit there, `/reload` in game, commit and push.

## How it fits together

- Morphing is done by **VanillaHelpers.dll** (v1.1.0+, OctoLauncher's `vanillaHelpers` mod), through its Lua API: `SetUnitDisplayID`, `SetUnitVisibleItemID`, `UnitDisplayInfo`. The addon never touches game memory itself. The original DMorph DLL targets WotLK 3.3.5a and can't run on this client.
- `DmorphOcto.lua` is the core: state, wardrobe, catalogue search and chat commands. Public functions live on the `DmorphOcto` table and return `ok, message`; the chat commands and the window both call them.
- `UI.lua` is the window and the minimap button.
- `Share.lua` (1.8.0 protocol "DMO2", see its header): DMorph users see each other's morphs. Looks are base 36 ("<display> <mount> <slot letter+item>..."), sent once they stand still 1 s (at most 3 s late), only to the audience (DMorph users seen in a scan, or who asked about us, in the last 180 s) by the quietest way: group/raid/BG addon message, GUILD addon message if every outside listener is a guild mate, else the hidden password channel "DmorphShare" (1.7's "DmorphOcto" is left). "M <mount>" goes out at once on (dis)mount. Questions "Q name:fingerprint" are answered on the way they came, with "H <fingerprint>" if unchanged; a channel question someone else already asked is dropped from our queue. Looks are cached per realm in DmorphOctoAccount.peerCache (14 days): a remembered player shows at once and is asked with the fingerprint; no answer in 20 s = forgotten. ChatFrame_OnEvent is wrapped to drop every CHAT_MSG_CHANNEL* event for our channels. At most one message per 0.6 s on the channel (0.2 s hidden), mount first, then look, replies, questions. Receivers morph the sender through VanillaHelpers with any token whose UnitName matches: target, mouseover, party/raid, or the GUID with SuperWoW (UnitExists returns it). VanillaHelpers' source (gitea.com/D-C-M-Inc/VanillaHelpers, src/Morph.cpp): overrides are kept per GUID (g_overrides), any *player* unit works but CanAssist must pass ("Unit is not friendly."). Remote mount skins only go on through steady tokens (party/raid/GUID), because the override must come off when they dismount. Received display IDs must exist in the catalogue. Settings: DmorphOctoAccount.shareOff / othersOff.
- `Data/Creatures.lua`, `Data/Items.lua` and `Data/ClassicTags.lua` are generated by `tools/build_data.py` from the cmangos classic-db 1.12.1 dump. `Data/HiddenModels.lua` and `Data/HiddenItems.lua` come from the game's files (see 1.9.0). `Data/Models.lua` is generated by `tools/build_models.ps1` from the client's MPQs: every display ID in `CreatureDisplayInfo.dbc` that Creatures.lua doesn't name, flagged when it's not in stock 1.12.1 (patch.MPQ). Don't edit them by hand. Both creature files are sorted in Lua's byte order so `GetCreatureCatalog` merges them in one pass.
- Saved variables: `DmorphOctoDB` (per character, the current look) and `DmorphOctoAccount` (shared: outfits, minimap position, `ui` = list/grid and model filter).

## Data (1.3.0)

- `Data/Models.lua` kind column: 0 Turtle creature name, 1 model-file name, 2/3 the same for displays not in stock patch.MPQ. Creatures.lua entries are kind 0. `Data/ModelTags.lua`: boss / rare per (display, name) from Turtle ranks, mount per display (NPC mount displays + model files matching riding|mount|... but not MountainGiant).
- `Data/Looks.lua`: per "race:gender" the CreatureDisplayInfoExtra looks "id,skin,face,hair,hairColour,facial,pieces,outfit;" deduped, fewest clothes first. The creator morphs into these NPC displays: no DLL here can write PLAYER_BYTES (checked VanillaHelpers, ClassicAPI, SuperWoW, nampower, UnitXP strings), and item morphs don't show on NPC displays.
- `Data/ItemsExtra.lua` (tools/build_items.ps1): Turtle wearables from tools/data/turtle_items.tsv (ShellLab export) + the game's WDB itemcache, per slot, plus `DmorphOcto_ItemPending` (Atlas-CFM loot IDs and set pieces with unknown slot). OctoWoW has items beyond Turtle (e.g. 33000+ "Prophecy" tier variants, Atlas-CFM's "Vanilla Plus" ranges). The core looks pending IDs up after login (GetItemInfo, or ClassicAPI C_Item.RequestLoadItemDataByID + ITEM_DATA_LOAD_RESULT), 4 in flight, saved in DmorphOctoAccount.itemInfo.
- `Data/ItemSets.lua`: the client's ItemSet.dbc (patch-4), 352 sets with visible pieces.
- Favourites (1.4.0): DmorphOctoAccount.favourites = { { id = displayID, mount = true|nil } }, sanitized in InitDB. Right-click a tile or models-list row toggles one for the current "Morph: you/mount" target; the Favourites tab wears (SetDisplay / SetMount) or unstars them.
- 1.5.0, from the user's in-game report: SetUnitMountDisplayID held the mount model even on foot (the override rewrites the server's 0 on dismount), so mount skins are now applied by WatchMount only while riding: mount field > 0 without override = mounted (that moment's new buff textures = the mount buff), buff gone = dismounted, override cleared. db.mount = skin for all mounts, db.mountSkins[real] per mount, db.ridden. ClassicAPI IsMounted() reads the same field, so it can't see dismounts.
- Races + Creator are one tab. 1.6.0: < > is strict, M.StepLook / M.GetLookChoices only accept looks with the other four features equal (same outfit number preferred), else nothing changes and the status says so. The user twice reported clicks changing other numbers ("random"). Only ~20% of looks have a second choice per feature (measured), so rows show "n of m" and go grey at 1. Looks.lua field 8 = outfit number per race:gender (same gear = same number).
- 1.6.0 Mounts tab: list 290 px wide (List takes a width), "Your skin" box with a turning preview of MountPick() (ui.mountPick covers a click still at the gate), ticked/gold row, auto-scroll to it, up/down arrows (StepMount) = previous/next model in the filtered list. User asked for these after 1.5.0.
- Item data strings are kept after parsing (catalogs are rebuilt when looked-up items arrive); creature data strings are dropped.

## 1.9.0 (user's screenshot of the Races tab, 11 Oct 2026)

- The user asked to remove models/items that don't show, add every boss and mount, items and races "from all expansions", and make Races stop "working really randomly" (the screenshot showed the red 1.6.0 refusal "No Undead female NPC has another skin colour with this face, ..."). Later-expansion models, races, items and sets aren't in the 1.12 client's MPQs (and the server doesn't know the items): explained, not possible.
- Races: < > always moves its row to the next value the race's NPCs have (`M.StepLook` returns k, pos, n, changed). `FindLook` keeps rows by weight skin 32 > hair style 16 > hair colour 8 > face 4 > facial hair 2 > outfit 1 (each beats all below), then the closest number of clothes. Measured over all 20 race/genders: whatever the weights, only ~4% of clicks can keep every other face/hair row, and the outfit almost always changes, because every NPC look is a unique combination. So the status names changed face/hair rows, not the outfit. Real per-row customisation needs a DLL that overrides PLAYER_BYTES / PLAYER_BYTES_2 (none here can; VanillaHelpers' Morph.cpp only handles display, native display, mount, BYTES_0 and visible items).
- `Data/ClassicTags.lua` (build_data.py, cmangos classic-db): boss = Rank 3, ScriptName boss_*, or an elite spawned at most twice with HealthMultiplier >= 4 and either MechanicImmuneMask bit 0x800000 (most dungeon bosses: VanCleef, Rivendare, Pythas...) or only spawned in instance maps with HealthMultiplier >= 5; rare = Rank 2/4 otherwise. Mounts = every spell_template aura 78 (MOUNTED) EffectMiscValue creature's models + creature_template_addon.mount. Merged with ModelTags.lua in GetCreatureCatalog (boss wins). 174 -> 564 bosses.
- `Data/HiddenModels.lua` / `Data/HiddenItems.lua` (shipped empty; written by build_models.ps1 / build_items.ps1, both run by `tools/update_from_game.ps1`): the core skips those IDs in the model list, item lists, learned items and NPC looks. Models are hidden when the display isn't in CreatureDisplayInfo.dbc (Creatures.lua names from cmangos weren't checked before), the model file is missing, its M2 header isn't "MD20" version 256-257, M2Array vertices (0x44) or views (0x4C) are empty, or its first skin (display field 6, `<model dir>\<skin>.blp`) is missing. Items are hidden when their display (tools/data/classic_item_displays.tsv, or the item cache) isn't in ItemDisplayInfo.dbc or none of its strings (read column-agnostically with `Dbc.TryStr`, which only accepts offsets right after a NUL; INV_ icons skipped) names a file under Item\ObjectComponents\{Weapon,Shield,Shoulder,Head,Cape,Quiver,Ammo} (helmets with race suffixes _HuM...) or Item\TextureComponents\<8 regions>\<name>_U/_M/_F.blp. Safety valves: a model check flagging > 1/4 of what it looks at is switched off, > 1/4 of named displays hidden = none, per item slot > 1/4 = none; each prints a warning. MpqDbc.cs gained `ReadStart` (first sector only), `TryStr` and `GameFiles` (hash each name once, cached; fast enough for every item).
- `tests/make_game_fixture.py` builds a fake game folder with real-format MPQs and DBCs; the cloud session ran both PowerShell scripts on it with PowerShell 7 (see the file's docstring for the expected output).

## Previews (ClassicAPI)

- `Model:SetDisplayInfo(id)` comes from ClassicAPI.dll (installed here, optional in code: `ui.canPreview`). Source: brues-code/ClassicAPI `src/model/DisplayInfo.cpp`. It loads the model async; dressed NPCs (displays with a CreatureDisplayInfoExtra) are dressed through **at most 8 jobs at once**, so the grid has 8 tiles. NPC weapons never show.
- A model frame draws white until its textures load (the "white flash"). Every model loads at a frame level below an opaque layer and is raised above it after `REVEAL` (0.45 s): tiles have a cover frame; the character preview has two PlayerModels behind/in front of the backdrop art and swaps them. Never call `SetUnit` on the visible preview model.
- WoW.exe's method names: plain `Model` has SetFacing/GetFacing, SetCamera, SetLight, SetModelScale, SetPosition, GetModel; `SetRotation`/`SetUnit` are PlayerModel-only (Blizzard's FrameXML only rotates PlayerModels with SetRotation). The mock enforces this.

## Rules for this code

- **Lua 5.0**: no `#`, no `%` (use `math.mod`), no `string.match`/`gmatch` (use `strfind`/`string.gfind`), no `select()`, no `...` in functions. `table.getn` counts element by element, so long lists keep their own `count`. At most 32 upvalues per function.
- **1.12 UI API**: script handlers take no arguments and read the globals `this`, `event`, `arg1`. There's no `SetSize` (use `SetWidth`/`SetHeight`), no `SetNumeric`, no `hooksecurefunc`. Lists use `FauxScrollFrameTemplate`. Templated frames need a name.
- Regions that share a draw layer have no fixed order in this client (learned in OctoBG): anything that must stack goes on child frames with explicit `SetFrameLevel`.
- Never use `GameTooltip:SetHyperlink` on an item the client may not have cached: it disconnects 1.12 clients.
- The trig functions' units depend on how the client was built, so avoid them (the minimap button uses plain vectors).
- Don't name custom widget fields `name`, `kind`, `text` (on frames that get SetText), `level`: the mock stores its own state there.

## Testing

- `powershell -ExecutionPolicy Bypass -File tools\run_tests.ps1` on this PC (no Lua or Python installed): builds `tools/LuaHost` (.NET 8) and runs `tests/run_tests.lua` on OBS Studio's `lua51.dll` (LuaJIT) with Lua 5.0 shims. Elsewhere: `lua tests/run_tests.lua` with Lua 5.0.
- LuaJIT accepts `#`/`%`/`...`, so also run the Lua 5.0 checker: `..\OctoBG\tools\LuaCheck.ps1 -Globals -Files <full paths>` (pass an array of paths).
- `tests/mock_wow.lua` is a strict 1.12 UI mock: it errors on methods, templates, fonts and script names the client doesn't have. Add any new widget method there only after confirming it exists in 1.12 (Blizzard's 1.12 FrameXML via `..\OctoBG\tools\MpqRead.ps1`, the method-name strings in WoW.exe, or a 1.12 addon here such as pfUI). ClassicAPI's `SetDisplayInfo` exists only while `Mock.classicAPI` is set.
- In game: `/console scriptErrors 1` to see Lua errors, and `/reload` after edits. `/dmorph status` shows whether VanillaHelpers is loaded.
